200 OK, vì request line đã đủ phương thức, đường dẫn và phiên bản.
B

Không trả lời, vì server chờ thêm header.

    Slide 2. Message HTTP/1.1: dòng đầu, các header, một dòng trống, rồi body

    Kết luận:
    • **Đặc tả giao thức**: dòng đầu, header, dòng trống, body; mỗi dòng kết thúc bằng **CRLF**; body dài đúng Content-Length.

    Đặc tả giao thức, hay protocol specification, là văn bản quy định chính xác những gì hai bên gửi cho nhau. Hình là một request và một response thật của ptit.edu.vn. Request mở đầu bằng request line, gồm phương thức GET, đường dẫn và phiên bản giao thức. Tiếp theo là các header, mỗi header một dòng, như Host cho biết tên miền của web server. Một dòng trống kết thúc phần header. Response mở đầu bằng status line, gồm phiên bản, mã trạng thái 301 và câu mô tả Moved Permanently, rồi cũng đến các header và một dòng trống. Sau dòng trống là body, dài đúng 178 byte như header Content-Length báo trước. Đặc tả còn hai quy định dùng suốt phần này: mỗi dòng kết thúc bằng CRLF, và HTTP/1.1 bắt buộc có header Host. Đặc tả đủ chi tiết như vậy thì client và server do hai người viết độc lập vẫn trao đổi được với nhau.

    Slide 3. NetCat đóng vai client với web server thật, và vai server với curl

    Kết luận:
    • **NetCat** ở cả hai vai: thử giao thức trên dữ liệu thật, **chưa cần viết mã**. Vai server chạy trên **loopback** `127.0.0.1`.

    Để nói HTTP bằng tay, mình dùng NetCat, công cụ dòng lệnh đọc từng dòng từ bàn phím, gửi qua một kết nối TCP, và in ra mọi dòng nhận được. Bản NetCat viết bằng Java của học phần có thêm một tùy chọn để kết thúc mỗi dòng gửi đi bằng CRLF, như HTTP quy định. Ở vai client, NetCat kết nối tới web server ptit.edu.vn, port 80, mình gõ request và đọc response của server. Ở vai server, NetCat lắng nghe ở port 9199, lệnh curl gửi request tới, mình đọc request đó rồi gõ response. Kết nối của vai server đi qua địa chỉ 127.0.0.1, gọi là loopback, trỏ về chính máy đang chạy, nên dữ liệu đi qua TCP mà không rời khỏi máy. Ở cả hai vai, giao thức được thử trên dữ liệu thật, khi chưa viết dòng mã nào.

    Slide 4. Vai client: gõ request, web server trả 301 kèm địa chỉ mới

    • Dòng bắt đầu bằng `>`: dòng **gõ vào** và gửi đi; các dòng khác: dòng **nhận được**. Dòng rỗng in thành `(empty line)`
    run.sh
    java -cp out netlab.tools.NetCat --crlf ptit.edu.vn 80

    Đây là bản ghi màn hình của vai client. Mình gõ bốn dòng: request line GET, header Host, header Connection với giá trị close để server đóng kết nối sau response, và một dòng trống. Trong bản ghi, dòng bắt đầu bằng dấu lớn hơn là dòng gõ vào và gửi đi, các dòng còn lại là dòng nhận được. Server trả status line HTTP/1.1 301 Moved Permanently, tức tài nguyên đã chuyển chỗ. Trong các header, Content-Length báo body dài 178 byte, còn Location chỉ địa chỉ mới, bản HTTPS của trang. Sau dòng trống là body HTML đúng 178 byte, rồi server đóng kết nối. Một web server thật đã hiểu request mình gõ tay, vì request đúng đặc tả.

    Slide 5. Vai server: đọc request của curl, gõ response, curl in ra hello

    • Phía curl nhận đúng response gõ tay và in `hello`: response hợp lệ theo đặc tả
    • `Content-Length: 7`: năm chữ cái và hai byte CRLF của dòng `hello`
    run.sh
    java -cp out netlab.tools.NetCat --crlf -l 9199
curl -i http://127.0.0.1:9199/hello.txt

    Ở vai server, NetCat lắng nghe ở port 9199, còn ở terminal khác, lệnh curl gửi một request GET tới NetCat. NetCat in ra đúng request của curl: request line GET, header Host ghi 127.0.0.1 kèm port, header User-Agent cho biết chương trình gửi là curl, header Accept, rồi một dòng trống. Mình gõ response theo đặc tả: status line 200 OK, header Content-Type, header Content-Length, một dòng trống, và body là dòng hello. Phía curl, response hiện ra đầy đủ, với dòng hello ở cuối. Các bạn để ý Content-Length bằng 7, không phải 5: dòng hello gõ vào kết thúc bằng CRLF, nên body gồm năm chữ cái và hai byte của CRLF.

    Slide 6. curl gửi đúng request mà mình đã gõ tay

    • `>`: request curl gửi; `<`: response của server; `*`: thông tin của curl

    curl -sv -o /dev/null http://ptit.edu.vn 2>&1 | head -14

    Slide 7. Thiếu header Host thì server trả 400; gửi đúng CRLF

    • HTTP/1.1 **bắt buộc header Host**: thiếu thì server trả 400 Bad Request
    • Bên gửi gửi đúng **CRLF**; bên nhận nên chấp nhận cả LF, nhưng không phải chương trình nào cũng vậy
    requests/no-host.txt
    GET / HTTP/1.1

    Đặc tả còn những quy định dễ bỏ sót khi gõ tay. Lần này mình chỉ gõ request line rồi một dòng trống, quên header Host. Các bạn thử đoán server trả lời thế nào. Kết quả là status line HTTP/1.1 400 Bad Request, tức request sai đặc tả. Lý do là HTTP/1.1 bắt buộc header Host, vì nhiều trang web có thể chạy chung một địa chỉ IP, và server cần biết request dành cho trang nào. Về ký tự kết thúc dòng, RFC 9112 quy định bên gửi dùng CRLF, và cho phép bên nhận chấp nhận cả LF. Khi mình thử gửi chỉ LF, web server của ptit.edu.vn vẫn trả lời bình thường, nhưng một chương trình tự tách dòng chỉ theo CRLF thì sẽ không thấy dòng nào kết thúc. Vì vậy, chương trình gửi luôn dùng đúng CRLF, còn chương trình nhận nên chấp nhận cả LF.

    Câu hỏi tương tác 1

    Câu hỏi đầu kiểm tra quy định về header Host.

    Câu hỏi: Gõ request bằng NetCat tới một web server: chỉ có dòng GET / HTTP/1.1 rồi một dòng trống, không có header Host. Server trả lời thế nào?
    • A. 200 OK, vì request line đã đủ phương thức, đường dẫn và phiên bản.
    • B. 301 Moved Permanently, chuyển sang trang HTTPS.
    • C. 400 Bad Request, vì HTTP/1.1 bắt buộc header Host.
    • D. Không trả lời, vì server chờ thêm header.
    Đáp án đúng: C — RFC 9112 bắt buộc request HTTP/1.1 có header Host; thiếu thì server trả 400 Bad Request. Dòng trống đã kết thúc phần header nên server không chờ thêm.

    Đáp án là C. Phương án D dễ được chọn vì có vẻ server còn chờ, nhưng dòng trống đã báo hết phần header, và server trả 400 ngay. Request line đủ ba phần vẫn chưa đủ, vì HTTP/1.1 bắt buộc header Host.

    Lưu ý dựng: Dừng video, hiện câu hỏi H5P. Sau khi người học trả lời: slide câu hỏi với đáp án C được tô xanh, các đáp án còn lại mờ đi, trong lúc đọc đoạn đáp án.

    Câu hỏi tương tác 2

    Câu cuối cùng quay lại ký tự kết thúc dòng.

    Câu hỏi: Theo đặc tả HTTP/1.1, mỗi dòng header trong một request kết thúc bằng gì?
    • A. Chỉ LF, như một dòng văn bản thông thường.
    • B. CRLF: hai byte CR rồi LF.
    • C. Dấu chấm phẩy.
    • D. Không có ký tự kết thúc, vì mỗi header có độ dài cố định.
    Đáp án đúng: B — RFC 9112 quy định mỗi dòng của HTTP/1.1 kết thúc bằng CRLF; một dòng trống (chỉ có CRLF) kết thúc phần header. curl -v không in hai ký tự này.

    Đáp án là B. Nhìn kết quả của curl, các bạn có thể nghĩ mỗi dòng chỉ kết thúc bằng LF như phương án A, vì curl không in ký tự CR ra. Nhưng theo RFC 9112, mỗi dòng của HTTP/1.1 kết thúc bằng CRLF.

    Lưu ý dựng: Như câu hỏi 1: dừng video, hiện H5P, sau đó tô xanh đáp án B.

    Tổng kết

    • **Đặc tả giao thức** HTTP/1.1 (RFC 9110, RFC 9112): dòng đầu, header, dòng trống, body theo Content-Length; mỗi dòng **CRLF**
    • **NetCat** nói HTTP bằng tay: vai client tới web server thật, vai server trên **loopback** cho **curl**
    • Header Host bắt buộc; gửi đúng CRLF, nhận thì khoan dung

    Đặc tả HTTP/1.1 quy định một message gồm dòng đầu, các header, một dòng trống, rồi body dài đúng Content-Length, và mỗi dòng kết thúc bằng CRLF. Nói giao thức bằng tay với NetCat cho thấy điều đó ở cả hai vai: web server thật hiểu request mình gõ, còn curl hiểu response mình gõ. Đặc tả còn những quy định dễ bỏ sót, như header Host bắt buộc và ký tự kết thúc dòng. Phần này để lại năm từ khóa: đặc tả giao thức, NetCat, curl, loopback và CRLF.

    Mở rộng

    Muốn biết các giao thức Internet được đặc tả thế nào, các bạn có thể đọc thêm RFC 9112, rồi thử nói một giao thức theo dòng khác bằng NetCat, như SMTP, giao thức gửi thư. Bài tập mở rộng là gửi request HEAD bằng NetCat tới một web server, rồi đối chiếu response với request GET theo RFC 9110.

    Tổng kết chương

    • **Định danh**: đích đến là endpoint = địa chỉ IP + port; tên miền qua phân giải tên
    • **Giao vận**: TCP cho byte stream tin cậy, UDP cho datagram; client–server hay P2P
    • **Stream**: contract của read, decorator, flush; DataStream, serialization; charset, framing
    • **Bài toán ứng dụng**: nói HTTP/1.1 bằng tay với NetCat ở cả hai vai, đối chiếu đặc tả và curl

    Chương 1 khép lại với bốn ý. Nhóm định danh trả lời đích đến là gì: endpoint, gồm địa chỉ IP và port, có được sau bước phân giải tên. Nhóm giao vận trả lời gửi bằng dịch vụ nào: TCP cho byte stream tin cậy, UDP cho datagram độc lập, cùng hai mô hình client–server và P2P. Nhóm stream trả lời đọc ghi dữ liệu thế nào: đúng contract của read, bọc stream bằng decorator và gọi flush trước khi chờ phản hồi. Trên byte stream, dữ liệu có kiểu đi qua DataStream, đối tượng qua serialization, còn văn bản cần charset và framing. Bài toán ứng dụng gom tất cả trên HTTP/1.1: đặc tả rõ ràng, và nói bằng tay được ở cả hai vai.
