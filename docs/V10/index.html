    Kết luận:
    • **Server tuần tự**: vòng ngoài accept từng kết nối, vòng trong trả lời từng request; kết nối sau chờ trong backlog.

    Trước khi viết mã, mình xem thiết kế của server. Vòng lặp ngoài bắt đầu bằng lời gọi accept, lấy một kết nối khỏi backlog. Với kết nối đó, server chạy một vòng lặp trong: đọc request line và các dòng header, tìm file trong thư mục www, gửi status line, header và nội dung file, rồi gọi phương thức flush để gửi đi ngay. Từ HTTP/1.1, một kết nối mặc định gửi được nhiều request lần lượt, gọi là persistent connection, nên vòng trong lặp lại cho request kế tiếp. Vòng lặp trong dừng khi lời gọi readLine trả về null, tức client đã đóng kết nối, hoặc khi hết read timeout. Server đóng kết nối, rồi quay lại lời gọi accept để lấy kết nối tiếp theo. Trong lúc đó, các kết nối khác đã bắt tay xong vẫn nằm chờ trong backlog. Cách tổ chức này gọi là server tuần tự, hay iterative server: các kết nối được phục vụ lần lượt, mỗi lần một kết nối.

    void serve() {
    while (!listener.isClosed()) {
        try (Socket connected = listener.accept()) {  // một kết nối tại một thời điểm
            connected.setSoTimeout(5_000);  // read timeout: client không gửi gì quá 5 giây

        } catch (IOException e) {  // gồm cả SocketTimeoutException: lỗi của một kết nối không dừng server
            log.println("connection error: " + e.getMessage());
        }
    }

    Phương thức serve chứa vòng lặp ngoài. Lời gọi accept đặt trong khối try-with-resources, nên connected socket luôn được đóng khi phục vụ xong. Server đặt read timeout 5 giây cho kết nối, ghi log 4-tuple, rồi chuyển kết nối cho phương thức handle. Trong log, mỗi dòng accepted đi kèm request của kết nối đó và dòng closed, rồi kết nối sau mới được nhận.

    Slide 5. Vòng lặp trong: đọc request, tìm file, gửi status line, header và body

    src/netlab/web/WebServer.java
    String[] parts = requestLine.split(" ");  // phương thức, đường dẫn, phiên bản
String path = parts[1].equals("/") ? "/index.html" : parts[1];
Path file = root.resolve(path.substring(1));  // đường dẫn trong thư mục www/

    return send(out, "404 Not Found", "text/plain; charset=utf-8", "404 Not Found\n".getBytes(UTF_8));
}
return send(out, "200 OK", contentType(path), Files.readAllBytes(file));
static String send(OutputStream out, String status, String type, byte[] body) throws IOException {
    String head = "HTTP/1.1 " + status + "\r\n"
            + "Content-Type: " + type + "\r\n"
            + "Content-Length: " + body.length + "\r\n"  // client biết body dài bao nhiêu byte
            + "\r\n";

    Vòng lặp trong nằm ở phương thức handle, không có trên slide: mỗi vòng đọc request line, đọc bỏ các dòng header cho tới dòng trống, rồi gọi phương thức respond. Phương thức send ghi status line, header Content-Type cho biết loại nội dung, header Content-Length cho biết body dài bao nhiêu byte, một dòng trống, rồi đến body. Mỗi dòng kết thúc bằng CRLF, như HTTP quy định. Mình thử bằng curl: hai lần đầu chỉ in mã trạng thái và loại nội dung, lần cuối dùng tùy chọn i để in cả header.     Slide 7. Một client không gửi gì làm mọi client sau phải chờ

    • curl đến sau **1 giây**: nhận response sau **4,06 giây**, thay vì vài mili giây
    • Server tuần tự bị chặn ở `readLine()` của kết nối đầu; kết nối sau đã bắt tay xong, **nằm chờ trong backlog**

    Server tuần tự còn một giới hạn. Mình chạy một client chỉ kết nối mà không gửi request nào, như một trình duyệt mở sẵn kết nối nhưng chưa dùng tới, và một giây sau chạy curl. Các bạn thử đoán curl chờ bao lâu.     Câu hỏi tương tác 1

    Câu hỏi đầu dùng lại bảng 4-tuple của ba kết nối.

    Câu hỏi: Ba client trên cùng một máy kết nối lần lượt tới web server ở port 9199. Ba kết nối được phân biệt bằng gì?
    • A. Bằng 4-tuple: địa chỉ và port của hai đầu; ở đây ba kết nối khác nhau ở port client.
    • B. Server cấp cho mỗi kết nối một port mới sau khi accept.
    • C. Bằng thứ tự gọi accept: kết nối thứ nhất, thứ hai, thứ ba.
    • D. Bằng địa chỉ IP của client.
    Đáp án đúng: A — Một kết nối TCP được định danh bằng 4-tuple. Cả ba kết nối có local port 9199 và cùng địa chỉ 127.0.0.1 ở hai đầu; chỉ port client (ephemeral port) khác nhau. Server không cấp port mới cho kết nối.

    Đáp án là A. Phương án B là hiểu nhầm phổ biến, nhưng log cho thấy cả ba kết nối đều có local port 9199: server không cấp port mới cho kết nối. Phương án D cũng không đủ, vì ba client chạy trên cùng một máy, cùng địa chỉ 127.0.0.1.
