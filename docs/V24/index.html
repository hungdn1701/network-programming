Java@WebService(serviceName = "LookupService", targetNamespace = "http://netlab/lookup")
public class LookupWebService {
    @WebMethod
    public String lookup(@WebParam(name = "key") String key) {  // thao tác lookup, tham số tên key trong message
        return DATA.get(key);
    }
}

SOAP nặng: message dài, xử lý XML tốn tài nguyên, nhiều chuẩn mở rộng

  • Một lần tra cứu: request 205 byte, response 250 byte XML; giao thức dòng ở Chương 2 chỉ cần 6 và 31 byte
  • Mỗi đầu phải phân tích XML và namespace: tốn CPU và bộ nhớ hơn nhiều so với đọc một dòng
  • Họ chuẩn mở rộng WS-* (bảo mật, giao dịch, gửi tin cậy…) làm hệ thống phức tạp
Lưu ý: SOAP vẫn có mặt trong hệ thống ngân hàng, dịch vụ công; API trên web chuyển dần sang REST.

    Slide 1. Gọi dịch vụ từ ngôn ngữ khác: cần hợp đồng và message chung

    • RMI: stub, serialization, giao thức đều là cơ chế **riêng của Java**
    • Cần một **hợp đồng** mô tả thao tác và kiểu dữ liệu, không phụ thuộc ngôn ngữ
    • Cần một **định dạng message** mọi ngôn ngữ đọc được, truyền qua giao thức sẵn có: **HTTP**
    Trọng tâm: **Câu hỏi của phần:** SOAP message có cấu trúc thế nào, và WSDL mô tả dịch vụ ra sao để ngôn ngữ nào cũng gọi được?

    Với RMI, mọi thứ giữa hai đầu đều là cơ chế riêng của Java: stub do JDK sinh, tham số đi qua serialization của Java, và giao thức truyền cũng chỉ RMI runtime hiểu. Để ngôn ngữ khác gọi được, lời gọi từ xa cần hai thứ. Thứ nhất là một hợp đồng mô tả dịch vụ có những thao tác nào, tham số và kết quả thuộc kiểu gì, viết ở dạng không phụ thuộc ngôn ngữ. Thứ hai là một định dạng message mà ngôn ngữ nào cũng đọc được, truyền qua một giao thức có ở mọi nơi là HTTP. Dịch vụ cung cấp thao tác theo cách đó gọi là web service, tức dịch vụ gọi qua giao thức web; SOAP và WSDL là cặp chuẩn đầu tiên cho loại dịch vụ này, SOAP cho message, WSDL cho hợp đồng. Vậy SOAP message có cấu trúc thế nào, và WSDL mô tả dịch vụ ra sao để ngôn ngữ nào cũng gọi được?

    Slide 2. SOAP message: Envelope bọc Header và Body, đi trong một HTTP POST

    Kết luận:
    • **SOAP**: lời gọi và kết quả là message **XML**; **SOAP envelope** chứa Header tùy chọn và Body mang thao tác, tham số.

    Trước hết là message. SOAP là giao thức đóng gói lời gọi và kết quả thành message XML, thường truyền qua HTTP. Các bạn nhìn request ở bên trái: đó là một HTTP POST tới đường dẫn lookup, với kiểu nội dung text/xml. Thân request là SOAP envelope, phần tử gốc của message, gồm phần Header tùy chọn cho các thông tin như bảo mật hay giao dịch, và phần Body. Phần Body mang lời gọi: phần tử lookup cho biết tên thao tác, còn phần tử con key chứa tham số, khóa hanoi. Response ở bên phải có cùng cấu trúc, và Body của nó chứa kết quả trong phần tử return. Ở cả hai chiều, XML thay cho serialization của Java, vì đây là dạng văn bản mà ngôn ngữ nào cũng có thư viện đọc ghi.

    Lưu ý dựng: Hình soap-message: ba bước của hình, bước 4 là ô kết luận. Hiện dần: bước 1 khi đọc “Các bạn nhìn request”; bước 2 khi đọc “Phần Body mang lời gọi”; bước 3 khi đọc “Response ở bên phải”; bước 4 khi đọc “Ở cả hai chiều”.

    Slide 3. WSDL là hợp đồng: từ đó mỗi ngôn ngữ tạo stub của mình

    Kết luận:
    • **WSDL** mô tả thao tác, kiểu dữ liệu và endpoint; công cụ của từng ngôn ngữ đọc WSDL để tạo stub.

    Client ở ngôn ngữ khác biết phải gửi message như thế nào nhờ WSDL, hay Web Services Description Language, tài liệu XML mô tả web service. Server tự sinh WSDL và công bố ngay tại endpoint. Hai phần đầu mô tả dịch vụ có gì: phần types định nghĩa kiểu dữ liệu, ở đây phần tử lookup có trường key kiểu chuỗi; phần portType liệt kê thao tác lookup với message vào và message ra. Hai phần sau mô tả gọi bằng gì và ở đâu: phần binding chọn SOAP qua HTTP, phần service ghi địa chỉ endpoint. Từ cùng một WSDL, mỗi ngôn ngữ có công cụ tạo stub: Java có công cụ wsimport, C# có công cụ dotnet-svcutil, còn thư viện zeep của Python đọc WSDL ngay lúc chạy. Như vậy, vai trò của remote interface trong RMI được thay bằng WSDL, một hợp đồng không gắn với ngôn ngữ nào.

    Slide 4. Server SOAP: vài chú thích và một lời gọi publish

    src/main/java/netlab/soap/LookupWebService.java
    @WebService(serviceName = "LookupService", targetNamespace = "http://netlab/lookup")
public class LookupWebService {
    @WebMethod
    public String lookup(@WebParam(name = "key") String key) {  // thao tác lookup, tham số tên key trong message
        return DATA.get(key);
    }
}

    Áp dụng vào dịch vụ tra cứu, mình dùng Jakarta XML Web Services, bộ API chuẩn cho SOAP. Từ JDK 11, API này không còn nằm sẵn trong JDK, nên mình lấy bản hiện thực Metro qua Maven. Trong lớp LookupWebService trên slide, mình chỉ thêm chú thích WebService cho lớp và chú thích WebMethod cho phương thức; chú thích WebParam đặt tên key cho tham số trong message. Ngoài slide còn một lớp khởi động nhỏ, SoapServer, chỉ gọi phương thức publish của lớp Endpoint với địa chỉ của dịch vụ, port 9199, đường dẫn lookup; Metro nhận request bằng HTTP server có sẵn trong JDK. Mình không viết dòng nào đọc hay ghi XML. Log của server in địa chỉ endpoint, địa chỉ WSDL, và một lời gọi lookup với khóa hanoi gửi tới từ curl.

    Lưu ý dựng: Mã phía trên, log của server phía dưới. Highlight @WebService, @WebMethod, @WebParam theo lời đọc. Hiện dần: bước 1 khi đọc “Log của server”.

    Slide 5. Gửi SOAP request bằng curl và đọc response XML

    request.xml
    <soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/" xmlns:lk="http://netlab/lookup">
  <soap:Body>
    <lk:lookup>
      <key>hanoi</key>
    </lk:lookup>
  </soap:Body>
</soap:Envelope>

    Vì SOAP chỉ là XML trong một HTTP POST, curl gửi được request mà không cần stub nào. File request.xml chứa SOAP envelope có Body là phần tử lookup với khóa hanoi; namespace của phần tử lookup phải khớp targetNamespace của dịch vụ, đúng như WSDL đã mô tả. Mình gửi file này bằng curl, với header Content-Type là text/xml, rồi định dạng lại response cho dễ đọc. Các bạn thử đoán: để gửi một khóa dài 5 byte, request SOAP dài bao nhiêu byte? Kết quả: mã trạng thái 200, và phần tử return trong SOAP envelope trả về mang giá trị của khóa hanoi. Kích thước mới là điều đáng chú ý: request dài 205 byte, response dài 250 byte, chưa kể header HTTP.

    Lưu ý dựng: XML request phía trên, kết quả phía dưới. Sau câu "dài bao nhiêu byte", dừng khoảng 2 giây trước khi khung kết quả hiện. Highlight <key>hanoi</key> trong request, <return> và dòng kích thước trong kết quả. Hiện dần: bước 1 khi đọc “Kết quả”.

    Slide 6. SOAP nặng: message dài, xử lý XML tốn tài nguyên, nhiều chuẩn mở rộng

    • Một lần tra cứu: request **205 byte**, response **250 byte** XML; giao thức dòng ở Chương 2 chỉ cần 6 và 31 byte
    • Mỗi đầu phải phân tích XML và namespace: tốn CPU và bộ nhớ hơn nhiều so với đọc một dòng
    • Họ chuẩn mở rộng **WS-*** (bảo mật, giao dịch, gửi tin cậy…) làm hệ thống phức tạp
    Trọng tâm: **Lưu ý:** SOAP vẫn có mặt trong hệ thống ngân hàng, dịch vụ công; API trên web chuyển dần sang REST.

    Để độc lập với ngôn ngữ, SOAP phải trả ba cái giá. Trước hết là kích thước: một lần tra cứu cần 205 byte request và 250 byte response, trong khi giao thức dòng ở Chương 2 chỉ cần 6 byte cho khóa hanoi kèm LF, và 31 byte cho phản hồi. Thứ hai là chi phí xử lý: mỗi đầu phải phân tích cây XML và namespace, tốn CPU và bộ nhớ hơn nhiều so với đọc một dòng. Cuối cùng là độ phức tạp: quanh SOAP có cả một họ chuẩn mở rộng WS-*, cho bảo mật, giao dịch, gửi tin cậy, và hệ thống càng dùng nhiều chuẩn càng khó cấu hình. Dù vậy, SOAP vẫn có mặt trong các hệ thống cần hợp đồng chặt và các chuẩn mở rộng ấy, như ngân hàng hay dịch vụ công; còn API trên web chuyển dần sang REST.

    • A. Mã nguồn Java của lớp LookupWebService.
    • B. Thao tác, kiểu dữ liệu của tham số và kết quả, cách gọi (SOAP qua HTTP) và địa chỉ endpoint.
    • C. Dữ liệu tra cứu hiện có trên server.

    Câu hỏi: So với Java RMI, SOAP giải quyết giới hạn nào?
    • A. Lời gọi từ xa không còn thất bại vì mạng.
    • B. Message nhỏ hơn và xử lý nhanh hơn.
    • C. Server không cần chạy khi client gọi.
    • D. Client và server có thể viết bằng các ngôn ngữ khác nhau.
    Đáp án đúng: D — SOAP dùng message XML và hợp đồng WSDL không phụ thuộc ngôn ngữ, truyền qua HTTP. Lời gọi vẫn có thể thất bại vì mạng, và message XML lớn hơn, xử lý chậm hơn.

    Đáp án là D. Phương án B ngược với kết quả vừa đo: message XML của SOAP dài hàng trăm byte cho một khóa 5 byte, và mỗi đầu còn phải phân tích XML. Phương án A cũng sai, vì SOAP vẫn là lời gọi qua mạng và vẫn có thể thất bại như lời gọi RMI.

    Tổng kết

    • **Web service**: thao tác gọi qua HTTP, message và hợp đồng không phụ thuộc ngôn ngữ
    • **SOAP**: message **XML**; **SOAP envelope** gồm Header tùy chọn và Body mang thao tác, tham số
    • **WSDL**: hợp đồng mô tả thao tác, kiểu dữ liệu, endpoint; mỗi ngôn ngữ tạo stub từ WSDL

    Web service đưa lời gọi từ xa ra ngoài một ngôn ngữ: thao tác được gọi qua HTTP, với message và hợp đồng không phụ thuộc ngôn ngữ. Với SOAP, lời gọi và kết quả là message XML, trong đó SOAP envelope gồm Header tùy chọn và Body mang thao tác cùng tham số. WSDL đóng vai hợp đồng, mô tả thao tác, kiểu dữ liệu và endpoint, để mỗi ngôn ngữ tạo stub của mình. Năm từ khóa đi cùng SOAP là web service, SOAP, SOAP envelope, WSDL và XML.
