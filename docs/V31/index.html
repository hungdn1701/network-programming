    Slide 3. JWT: header, payload và chữ ký; API kiểm tra trước khi tin

    Kết luận:
    • **JWT**: header.payload.signature; **chữ ký số** chống sửa đổi, **claim** exp giới hạn thời hạn, **scope** quyết định quyền.

    Access token thường là JWT, hay JSON Web Token, gồm ba phần ngăn bởi dấu chấm: header, payload và signature, mỗi phần biểu diễn bằng Base64URL. Giải mã hai phần đầu từ Base64URL, không cần khóa nào, mình được header ghi thuật toán ký RS256, và payload chứa các claim: sub là người dùng, scope là các quyền, iat và exp là thời điểm cấp và thời điểm hết hạn. Phần signature là chữ ký số của authorization server trên chuỗi header chấm payload, ký bằng khóa riêng. API kiểm tra chữ ký bằng khóa công khai, nên không phải gọi authorization server cho mỗi request. Khi nhận token, API kiểm tra lần lượt: chữ ký sai hay token quá hạn thì trả 401, nghĩa là chưa xác thực được. Còn token hợp lệ nhưng thiếu scope write:pets thì API trả 403, nghĩa là không có quyền. Như vậy, chữ ký cho biết token do đúng authorization server cấp và chưa bị sửa, còn scope quyết định token được làm gì.

    Câu hỏi: API trả 403 cho một request PUT có kèm access token. Điều đó cho biết gì?
    • A. Request không có token.
    • B. Token hợp lệ, server biết người gọi là ai, nhưng người đó không có quyền ghi.
    • C. Chữ ký của token sai.
    • D. Token đã hết hạn.
    Đáp án đúng: B — 403 là lỗi phân quyền: xác thực đã thành công nhưng thiếu quyền (scope). Không có token, sai chữ ký, hết hạn đều là lỗi xác thực, trả 401.

    Đáp án là B. Ba phương án còn lại đều là lỗi xác thực, server trả 401: chưa có token, hoặc token không đáng tin. Mã 403 chỉ xuất hiện khi xác thực đã xong và vấn đề nằm ở quyền.

    Lưu ý dựng: Dừng video, hiện câu hỏi H5P. Sau khi người học trả lời: slide câu hỏi với đáp án B được tô xanh, các đáp án còn lại mờ đi, trong lúc đọc đoạn đáp án.

    Câu hỏi tương tác 2

    Câu sau xét chi phí kiểm tra token khi API nhận nhiều request.

    Câu hỏi: API nhận 1 000 request mỗi giây, mỗi request mang một JWT. Để kiểm tra token, API có cần gọi authorization server cho từng request không?
    • A. Có, vì chỉ authorization server biết token có hợp lệ.
    • B. Có, để giải mã payload.
    • C. Không, vì JWT không cần kiểm tra.
    • D. Không, API kiểm tra chữ ký bằng khóa công khai và tự đọc exp, scope trong token.
    Đáp án đúng: D — JWT mang sẵn claim và chữ ký; API kiểm tra chữ ký bằng khóa công khai của authorization server rồi đọc exp, scope ngay trong token.

    Đáp án là D. JWT mang sẵn các claim và chữ ký, nên API tự kiểm tra bằng khóa công khai của authorization server, không phải hỏi authorization server như phương án A. Phương án C là sai lầm nguy hiểm: token không được kiểm tra thì ai cũng tự viết được token.

    Lưu ý dựng: Như câu hỏi 1: dừng video, hiện H5P, sau đó tô xanh đáp án D.

    Tổng kết

    • **Xác thực**: người gọi là ai (lỗi: 401); **phân quyền**: người đó được làm gì (lỗi: 403)
    • **OAuth 2.0**: authorization server cấp **access token** với **scope**; API không giữ mật khẩu
    • **JWT**: kiểm tra chữ ký, exp, scope trước khi tin **claim**; payload không được mã hóa

    Xác thực trả lời người gọi là ai, và lỗi xác thực là 401. Phân quyền trả lời người đó được làm gì, và lỗi phân quyền là 403. Với OAuth 2.0, authorization server xác thực người dùng và cấp access token kèm scope, nên API không phải giữ mật khẩu. Access token dạng JWT mang claim và chữ ký số: API kiểm tra thuật toán, chữ ký, thời hạn rồi mới xét scope, và payload thì không được mã hóa. Từ khóa của phần gồm bảy mục: xác thực, phân quyền, OAuth 2.0, access token, JWT, claim và scope.

    Lưu ý dựng: Ba thẻ hiện lần lượt; hàng từ khóa hiện cuối. Hiện dần: bước 1 khi đọc “Xác thực trả lời”; bước 2 khi đọc “Với OAuth 2.0”; bước 3 khi đọc “Access token dạng JWT”; bước 4 khi đọc “Từ khóa của phần”.
